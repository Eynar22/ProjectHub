B1 — LOS 5 PRINCIPIOS QUE SOSTIENEN TODO
================================================================================

PRINCIPIO 1 — ORGANIZA POR FUNCIONALIDAD, NO POR TIPO DE ARCHIVO
    MAL:  /components (200 archivos), /hooks (80 archivos), /utils (50)
    BIEN: /features/eventos/{components, hooks, services, types}

    Por qué: cuando trabajas en "eventos", todo lo de eventos está en una sola
    carpeta. No saltas entre 6 carpetas para tocar una funcionalidad.
    Regla práctica: si borras una funcionalidad, deberías poder borrar UNA
    carpeta y que el proyecto siga compilando.

PRINCIPIO 2 — UN ARCHIVO, UNA RESPONSABILIDAD
    Un componente que hace fetch, transforma datos, valida un formulario y
    renderiza una tabla es cuatro archivos disfrazados de uno.
    Límite práctico: si un archivo pasa de 200-250 líneas, divídelo.

PRINCIPIO 3 — LAS DEPENDENCIAS FLUYEN EN UNA SOLA DIRECCIÓN
        pages  →  features  →  shared  →  lib
    Una página puede importar de features. Una feature puede importar de shared.
    shared NUNCA importa de features. Una feature NUNCA importa de otra feature
    directamente (si lo necesitas, ese código pertenece a /shared).

PRINCIPIO 4 — EL COMPONENTE NUNCA HABLA CON LA API
    Ningún componente contiene fetch() ni axios. Ni uno. El componente llama a
    un hook, el hook llama a un servicio, el servicio llama al cliente HTTP.
    Esta es la regla que más orden genera. Detalle completo en B4.

PRINCIPIO 5 — SI HAY QUE ELEGIR, GANA LA CONSISTENCIA
    Una convención mediocre aplicada en todo el proyecto vale más que la
    convención perfecta aplicada a medias. Elige una forma y no la cambies
    a mitad de proyecto.

================================================================================
B4 — LA CAPA DE API: LA REGLA MÁS IMPORTANTE DE ESTE ANEXO
================================================================================

[REGLA ABSOLUTA] Un componente NUNCA llama a la API directamente.
Nunca verás fetch() ni axios.get() dentro de un archivo .tsx de componente.

FLUJO OBLIGATORIO, SIEMPRE EN ESTE ORDEN:

    COMPONENTE  →  HOOK  →  SERVICIO  →  CLIENTE HTTP  →  BACKEND
     (.tsx)      (use*.ts)  (*.service.ts)  (client.ts)

    COMPONENTE   solo muestra datos y dispara acciones. No sabe que existe HTTP.
    HOOK         maneja estado del servidor: carga, error, caché, reintentos.
    SERVICIO     sabe qué endpoint llamar y con qué forma de datos.
    CLIENTE      sabe la URL base, los headers, el token y cómo manejar errores.

POR QUÉ ESTA SEPARACIÓN NO ES BUROCRACIA:
    - Si cambia la URL del backend, tocas 1 archivo (endpoints.ts).
    - Si cambia la forma de autenticar, tocas 1 archivo (client.ts).
    - Si el backend renombra un campo, tocas 1 archivo (el servicio).
    - Puedes probar la lógica sin levantar el backend.
    - Cuando algo falla, sabes exactamente en qué capa buscar.

    Sin esta separación, un cambio de endpoint significa buscar "axios" en 40
    archivos. Eso es exactamente lo que estamos evitando.

[REGLA] TODAS las rutas de la API viven en un solo archivo: lib/api/endpoints.ts
        Ninguna URL escrita a mano dentro de un servicio.
[REGLA] Un servicio por recurso del backend. Si NestJS tiene EventosController,
        el frontend tiene eventos.service.ts. Correspondencia 1 a 1.
[REGLA] El servicio devuelve DATOS, no respuestas HTTP. El componente no debe
        saber qué es un `response.data.data`.
[REGLA] El servicio no maneja estado ni muestra toasts. Solo pide datos.

 * Todas las rutas del backend en un solo lugar.
 * Si el backend cambia una ruta, este es el ÚNICO archivo que se toca.

export const ENDPOINTS = {
  AUTH: {
    LOGIN:            '/auth/login',
    LOGOUT:           '/auth/logout',
    REFRESH:          '/auth/refresh',
    PERFIL:           '/auth/perfil',
  },
  EVENTOS: {
    LISTAR:           '/eventos',
    CREAR:            '/eventos',
    DETALLE:  (id: string) => `/eventos/${id}`,
    ACTUALIZAR: (id: string) => `/eventos/${id}`,
    ELIMINAR: (id: string) => `/eventos/${id}`,
    CERRAR:   (id: string) => `/eventos/${id}/cerrar`,
  },
  ENTRADAS: {
    LISTAR:           '/entradas',
    POR_EVENTO: (eventoId: string) => `/eventos/${eventoId}/entradas`,
    VALIDAR_QR:       '/entradas/validar-qr',
  },
} as const;


/* ============================================================================
 * src/lib/api/client.ts
 * Instancia única de axios. Aquí vive TODO lo transversal:
 * URL base, headers, token de sesión, manejo global de errores y timeouts.
 * Ningún otro archivo del proyecto crea su propia instancia de axios.
 * ========================================================================= */

import axios, { AxiosError, AxiosInstance } from 'axios';
import { storage } from '@/lib/storage';
import { normalizarError } from './errors';

/** Timeout global. Si el backend no responde en 15s, se aborta. */
const TIMEOUT_MS = 15_000;

export const apiClient: AxiosInstance = axios.create({
  baseURL: import.meta.env.VITE_API_URL,
  timeout: TIMEOUT_MS,
  headers: { 'Content-Type': 'application/json' },
});

/* --- INTERCEPTOR DE PETICIÓN -------------------------------------------
 * Adjunta el token de sesión a cada llamada saliente.
 * Así ningún servicio tiene que acordarse de mandar el header. */
apiClient.interceptors.request.use((config) => {
  const token = storage.obtenerToken();
  if (token) {
    config.headers.Authorization = `Bearer ${token}`;
  }
  return config;
});

/* --- INTERCEPTOR DE RESPUESTA ------------------------------------------
 * 1. Desenvuelve el body: el componente recibe datos, no un objeto axios.
 * 2. Traduce cualquier error del backend a un formato único (ApiError).
 * 3. Si la sesión expiró (401), cierra sesión y manda al login. */
apiClient.interceptors.response.use(
  (response) => response,
  (error: AxiosError) => {
    if (error.response?.status === 401) {
      storage.limpiarSesion();
      window.location.href = '/login';
    }
    return Promise.reject(normalizarError(error));
  },
);


/* ============================================================================
 * src/lib/api/errors.ts
 * Convierte cualquier fallo (red, timeout, error de NestJS) en un ÚNICO
 * formato. El resto del proyecto solo conoce ApiError, nunca AxiosError.
 * ========================================================================= */

import { AxiosError } from 'axios';

export interface ApiError {
  /** Código HTTP, o 0 si el fallo fue de red. */
  status: number;
  /** Mensaje ya listo para mostrar al usuario, en español. */
  mensaje: string;
  /** Errores por campo, para pintar en formularios. */
  camposConError?: Record<string, string>;
}

/** Mensajes por defecto según el código HTTP. Nunca mostramos texto técnico. */
const MENSAJES_POR_STATUS: Record<number, string> = {
  0:   'No pudimos conectar con el servidor. Revisa tu conexión.',
  400: 'Los datos enviados no son válidos.',
  401: 'Tu sesión expiró. Inicia sesión de nuevo.',
  403: 'No tienes permiso para realizar esta acción.',
  404: 'No encontramos lo que buscabas.',
  409: 'Esta operación entra en conflicto con datos existentes.',
  422: 'Revisa los campos marcados.',
  500: 'Ocurrió un error en el servidor. Intenta de nuevo en unos minutos.',
};

export function normalizarError(error: AxiosError<any>): ApiError {
  const status = error.response?.status ?? 0;
  const cuerpo = error.response?.data;

  return {
    status,
    // Prioridad: mensaje del backend > mensaje por status > genérico
    mensaje:
      cuerpo?.message ??
      MENSAJES_POR_STATUS[status] ??
      'Ocurrió un error inesperado.',
    camposConError: cuerpo?.errors,
  };
}

/* ============================================================================
 * src/features/eventos/services/eventos.service.ts
 *
 * Responsabilidad: hablar con los endpoints de eventos del backend.
 * NO maneja estado. NO muestra mensajes. NO conoce React.
 * Devuelve datos ya tipados y listos para usar.
 * ========================================================================= */

import { apiClient } from '@/lib/api/client';
import { ENDPOINTS } from '@/lib/api/endpoints';
import type {
  Evento,
  CrearEventoDto,
  ActualizarEventoDto,
  FiltrosEvento,
} from '../types/eventos.types';

export const eventosService = {
  /** Lista los eventos, con filtros opcionales de estado y búsqueda. */
  async listar(filtros?: FiltrosEvento): Promise<Evento[]> {
    const { data } = await apiClient.get<Evento[]>(ENDPOINTS.EVENTOS.LISTAR, {
      params: filtros,
    });
    return data;
  },

  /** Obtiene un evento por su id. Lanza ApiError 404 si no existe. */
  async obtenerPorId(id: string): Promise<Evento> {
    const { data } = await apiClient.get<Evento>(ENDPOINTS.EVENTOS.DETALLE(id));
    return data;
  },

  /** Crea un evento nuevo y devuelve el evento ya creado con su id. */
  async crear(dto: CrearEventoDto): Promise<Evento> {
    const { data } = await apiClient.post<Evento>(ENDPOINTS.EVENTOS.CREAR, dto);
    return data;
  },

  /** Actualiza campos parciales de un evento existente. */
  async actualizar(id: string, dto: ActualizarEventoDto): Promise<Evento> {
    const { data } = await apiClient.patch<Evento>(
      ENDPOINTS.EVENTOS.ACTUALIZAR(id),
      dto,
    );
    return data;
  },

  /** Cierra el evento. Operación irreversible del lado del backend. */
  async cerrar(id: string): Promise<void> {
    await apiClient.post(ENDPOINTS.EVENTOS.CERRAR(id));
  },
};

REGLAS DE LOS SERVICIOS
--------------------------------------------------------------------------------
[REGLA] Un objeto exportado por recurso, no funciones sueltas. Facilita el
        autocompletado: escribes `eventosService.` y ves todo lo disponible.
[REGLA] Los métodos usan verbos del dominio: listar, obtenerPorId, crear,
        actualizar, eliminar, cerrar. Consistentes en TODOS los servicios.
[REGLA] Siempre tipa la respuesta: apiClient.get<Evento[]>(...)
[REGLA] El servicio no atrapa errores. Deja que suban al hook. El hook decide
        qué mostrar. Un try/catch dentro del servicio esconde problemas.
[REGLA] Si el backend devuelve un formato envuelto ({ data, meta }), desenvuelve
        AQUÍ. El componente jamás debe ver `.data.data`.

/* ============================================================================
 * src/features/eventos/types/eventos.types.ts
 * Espejo de las entidades y DTOs del backend NestJS.
 * Si el backend cambia una entidad, este archivo se actualiza primero.
 * ========================================================================= */

/** Estados posibles de un evento. Debe coincidir con el enum de Prisma. */
export enum EstadoEvento {
  SOLICITADO = 'SOLICITADO',
  APROBADO   = 'APROBADO',
  ACTIVO     = 'ACTIVO',
  FINALIZADO = 'FINALIZADO',
  RECHAZADO  = 'RECHAZADO',
}

/** Entidad tal como la devuelve el backend. Solo lectura. */
export interface Evento {
  id: string;
  nombre: string;
  descripcion: string;
  lugar: string;
  fechaInicio: string;      // ISO 8601. Se formatea al mostrar, no aquí.
  fechaFin: string;
  estado: EstadoEvento;
  clienteId: string;
  creadoEn: string;
}

/** Datos que se ENVÍAN al crear. Espejo del CreateEventoDto de NestJS. */
export interface CrearEventoDto {
  nombre: string;
  descripcion: string;
  lugar: string;
  fechaInicio: string;
  fechaFin: string;
}

/** Todos los campos opcionales: es un PATCH, no un PUT. */
export type ActualizarEventoDto = Partial<CrearEventoDto>;

/** Parámetros de consulta para el listado. */
export interface FiltrosEvento {
  estado?: EstadoEvento;
  busqueda?: string;
  pagina?: number;
  limite?: number;
}

REGLAS DE TIPOS
--------------------------------------------------------------------------------
[REGLA] Sufijo Dto para lo que ENVÍAS. Sin sufijo para lo que RECIBES.
        Evento (recibes) vs CrearEventoDto (envías).
[REGLA] Las fechas viajan como string ISO. Se convierten a Date solo en el

/* ============================================================================
 * src/features/eventos/hooks/useEventos.ts
 *
 * Responsabilidad: conectar el servicio con React.
 * Maneja carga, error, caché e invalidación. El componente solo consume.
 * ========================================================================= */

import { useQuery, useMutation, useQueryClient } from '@tanstack/react-query';
import { eventosService } from '../services/eventos.service';
import type { CrearEventoDto, FiltrosEvento } from '../types/eventos.types';

/** Claves de caché de esta feature. Centralizadas para invalidar sin errores. */
export const EVENTOS_KEYS = {
  todos: ['eventos'] as const,
  lista: (filtros?: FiltrosEvento) => ['eventos', 'lista', filtros] as const,
  detalle: (id: string) => ['eventos', 'detalle', id] as const,
};

/** Lista de eventos con filtros. Devuelve datos, carga y error ya listos. */
export function useEventos(filtros?: FiltrosEvento) {
  return useQuery({
    queryKey: EVENTOS_KEYS.lista(filtros),
    queryFn: () => eventosService.listar(filtros),
    staleTime: 60_000, // 1 min: evita refetch en cada render
  });
}

/** Crea un evento e invalida la lista para que se refresque sola. */
export function useCrearEvento() {
  const queryClient = useQueryClient();

  return useMutation({
    mutationFn: (dto: CrearEventoDto) => eventosService.crear(dto),
    onSuccess: () => {
      queryClient.invalidateQueries({ queryKey: EVENTOS_KEYS.todos });
    },
  });
}

[REGLA] Usa una librería de estado de servidor (TanStack Query o SWR). Manejar
        loading/error/caché a mano con useState + useEffect en cada componente
        es la fuente número uno de bugs y código duplicado.
[REGLA] Las claves de caché van centralizadas en un objeto KEYS por feature.
        Invalidar con strings sueltos genera bugs que no se ven hasta producción.
[REGLA] El hook es el único lugar donde conviven React y la API.

/* ============================================================================
 * src/features/RECURSO/services/RECURSO.service.ts
 * Responsabilidad: comunicación con los endpoints de RECURSO.
 * No maneja estado ni interfaz.
 * ========================================================================= */
import { apiClient } from '@/lib/api/client';
import { ENDPOINTS } from '@/lib/api/endpoints';
import type { Recurso, CrearRecursoDto } from '../types/RECURSO.types';

export const recursoService = {
  async listar(): Promise<Recurso[]> {
    const { data } = await apiClient.get<Recurso[]>(ENDPOINTS.RECURSO.LISTAR);
    return data;
  },
  async obtenerPorId(id: string): Promise<Recurso> {
    const { data } = await apiClient.get<Recurso>(ENDPOINTS.RECURSO.DETALLE(id));
    return data;
  },
  async crear(dto: CrearRecursoDto): Promise<Recurso> {
    const { data } = await apiClient.post<Recurso>(ENDPOINTS.RECURSO.CREAR, dto);
    return data;
  },
};
